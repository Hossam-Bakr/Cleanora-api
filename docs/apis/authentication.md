# Authentication API

Status: Implemented in R1-P02; phase remains In Progress pending final review and human approval.

Phase: R1-P02

The implemented routes, access rules, token transport, and response contract are
documented in:

- `docs/phases/release-1/R1-P02-authentication/api-contract.md`
- `docs/phases/release-1/R1-P02-authentication/security-session-design.md`
- `docs/apis/google-sign-in-frontend.md`

The implementation is capability-gated by `AUTH_ENABLED` and requires the
complete SMTP capability. Under DEC-028, every supported self-signup category
receives verification and recovery credentials at its account-bound email.
Phone values remain unverified and SMS is not part of R1-P02.

DEC-020 standardizes JSON failures as `code`, matching numeric `statusCode`,
safe descriptive `message`, optional field-level `details`, and `requestId`.
Signup reports whether a normalized phone or email is already registered so
the frontend can mark the correct field. Login and password recovery remain
enumeration-safe. New passwords use the shared 7–128 character
predictability-based policy; unpredictable numbers-only passwords are valid.
Validation failures return every independently detectable invalid field in one
`error.details.issues` array.
If both signup phone and email already exist, the same issues array reports
both conflicts. Passwords are never checked or disclosed as duplicate values.

The canonical cookies are `cleanora_refresh_token` for the rotating refresh
credential and `cleanora_google_oauth_state` for short-lived Google
correlation. `fs_refreshtoken` is not generated by this repository; the
authentication boundary expires it as known stale localhost state.

Google browser sign-in uses a backend callback followed by a safe frontend
redirect. Tokens and provider callback parameters are never placed in the
frontend redirect URL. New Google identities become active only when Google
asserts a verified email; R1-P02 exposes no Google phone-verification endpoint.
The backend never renders a Google result page. Chrome flows begin at
`/google/browser`, return through `/google/callback`, then redirect to the
configured frontend callback. The frontend calls `/refresh` with credentials
included and receives the access token plus canonical safe `user`.

The single canonical authentication Postman collection and
`docs/apis/openapi/r1-p02-authentication.yaml` are maintained with the live HTTP
contract. Final acceptance evidence remains open while R1-P02 is In Progress.
